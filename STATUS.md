## Corrections to earlier claims (found by actually running things)

- Table count was stated as 19 when the schema had 18 (now 19 after adding `user_tokens`).
- The `mkdir` commands used brace expansion under `sh`, creating literal `{a,b,c}` folders; the real directories did not exist.
- Startup crashed: raw-string `execute("SELECT 1")` (invalid in SQLAlchemy 2), MySQL-only `SET` on other dialects, calls to removed functions.
- ORM models used `Integer`/`String` for DECIMAL/DATE columns (weight 72.5 would have become 72); placeholder tables contradicted the schema.
- Validation errors returned HTTP 500 (non-serialisable exception objects in the response).
- `EmailStr` rejected `.local` addresses, so the spec's `admin@healthpredict.local` / `demo@healthpredict.local` could never log in.
- `tailwind.config.js` failed (`require` in an ES module, undeclared plugins, undefined `danger` colour): the web app did not build.
- Mobile `package.json` did not install (expo-router 2 vs Expo 50); `app.json` referenced six missing asset files.
- `requirements.txt` was unpinned-from-memory, listed two JWT libraries, and used a passlib/bcrypt combination with known issues.
- Root `.env.example` was reported as created but did not exist.
- **`user_profiles.exercise_frequency` / `smoking_status` / `alcohol_consumption` defaulted to `'SEDENTARY'`/`'NEVER'`/`'NEVER'` at the database level** (from Phase 1, before anything downstream consumed them). Once the health score started reading these fields, this meant a user who had told the app nothing would silently score as a confirmed non-smoker/non-drinker - an assumption presented as a fact. Fixed by removing the DB and ORM defaults; unset now genuinely means "not yet provided," and the score correctly reports those components as skipped instead.
- `glucose_caveat` in the assessment response fired even when no glucose was submitted (it checked "was the metabolic component included at all," which can happen via BMI alone). Fixed to check the actual glucose field.
- Pagination (`/admin/users`, `/health/assessment/history`) ordered by `created_at DESC` alone; with only second-level timestamp precision, rows created within the same second had no defined order. Fixed by adding `id DESC` as a tiebreaker in both places.
- Background services (MariaDB, uvicorn) started with `nohup ... &` in one tool call do not reliably survive into the next tool call in this environment - confirmed by repeated failures. Workaround adopted: every DB-dependent script begins with an idempotent "start MariaDB if it's not already up" guard, and live-server checks run start-to-finish inside a single call.
- The first training run used `n_jobs=-1` and large hyperparameter grids, assuming multiple CPU cores, and timed out at 300s with no output. `nproc` showed this environment has **one** CPU core; `n_jobs=-1` was actively counterproductive (worker processes contending for the single core). Fixed by removing all `n_jobs` parallelism and staging the pipeline (subsample for screening/tuning, full data only for the final fit/evaluation) - full run now completes in ≈22 seconds. Documented in `docs/ml-methodology.md` rather than hidden.
- A joint height/weight BMI outlier (90 rows, e.g. 122cm/161kg -> BMI 108) survived the initial per-column range filters because each value was individually plausible; found by inspecting the cleaned data's BMI distribution, not anticipated in advance. Added as a separate, documented filtering step.
- **Found only by running the real end-to-end flow, not by 180+ passing unit/integration tests:** `POST /api/health/assessment` crashed (500) for a realistic input (BMI 32.3, glucose 135). The Phase 3 rule-based score's metabolic component uses 0.55/0.45 weights, which - unlike every other component's 0.6/0.4 weights - can produce a fractional combined score (0.55×45 + 0.45×35 = 40.5) against an API field typed as a plain `int`. Every existing Phase 3 test happened to use inputs where both sub-scores landed on exactly 100, which trivially stayed whole - the gap was in test *data* variety, not test *count*. Fixed by rounding each component's displayed score; regression test added.
- While chasing that bug, a second, unrelated issue compounded it: the live-check script used `set -e`, so when the first failure occurred the script aborted *before* its cleanup step, leaving the old `uvicorn` process still bound to port 8000 and still serving the pre-fix code. The next verification attempt "failed" against code that had already been fixed, because it was hitting the stale process. Fixed by adding `trap 'kill $SERVER_PID' EXIT` and an explicit `pkill` of any stale server at the start of the script, and by resetting the dev database to a clean state before any live check that registers test accounts (an earlier run had reused `p5.demo@test.com` with an already-completed profile, which initially manufactured a misleading "pass").
- `goal_service._current_metric`'s HYDRATION branch had a ternary that accidentally returned `None` for "0ml logged today" - a case explicitly meant to be a valid 0%, not "no data" (and already covered by an existing `compute_progress` unit test asserting exactly that distinction). Caught by re-reading the code against its own already-written test intent before running anything, not by a failing test - fixed to a plain `float(total)` before it was ever exercised.
- A medicine-delete cascade test failed (`deleted medicine's schedule rows still present`) despite the actual DELETE working correctly. Root cause: the test's own `db` fixture session, under MySQL's default REPEATABLE READ isolation, took its consistency snapshot on an earlier query in the same test, before the `client.delete()` call committed through a *different* session - so the later assertion in that same session was reading stale data. Confirmed real cascade-delete behavior directly (same-session-after-commit and brand-new-session both showed 0 rows) before concluding it was a test-isolation artifact rather than a product bug. Fixed by calling `db.commit()` in the test between the mutating HTTP call and the next read, to start a fresh snapshot. This same pitfall could affect any future test that mixes a long-lived `db` fixture session with intervening `client` HTTP calls - worth remembering if a similarly "impossible" test failure shows up again.

## Known limitations

- Logout revokes the refresh token, but an already-issued access token stays valid until it expires (30 min).
- Rate limiting is in-memory, per process (fine for one server; use Redis if scaled out).
- Web stores tokens in `localStorage` (XSS trade-off, noted in `services/api.js`).
- No SMTP yet: reset/verification tokens are logged to the server console outside production. Email verification is recorded but does not gate login.
- Verified on MariaDB 10.11, not MySQL 8.0. Please run `schema.sql` and the test suite once on your MySQL 8 install.
- `Landing` page is fully implemented (Phase H) at `/`, featuring hero showcase, 68,569 patient trust metrics, 6 clinical feature cards, 3-step workflow, technology stack, and prominent healthcare disclaimer. Unauthenticated visitors can view features or sign in/register; authenticated users are routed to the dashboard.
- Admin actions are audit-logged (Phase F). Only account activation/deactivation exists as an admin action; other actions (e.g. role changes) are not offered.
- ML libraries are not in `backend/requirements.txt` yet; they are added in Phase 5 once tested.
- The health score is a rule-based formula, not the ML model - see `docs/health-scoring.md` for exactly what it does and does not account for (no fasting/random glucose distinction, no age/sex adjustment, hydration deliberately excluded until Phase 7).
- No frontend component/E2E tests (e.g. Playwright, React Testing Library) yet - only pure-logic unit tests and a successful production build. Visual/interaction bugs in the React pages would not be caught automatically.
- The ML model is now wired into `POST`/`GET /api/health/assessment`, but **backend/app/prediction_service.py duplicates** `ml/`'s `FEATURE_COLUMNS` and classification thresholds rather than importing them (a deliberate decoupling choice - see `docs/ml-methodology.md`'s Phase 5 section) - a drift test guards this, but it is still two copies of the same small fact, not one.
- The dataset's label (`cardio`) remains undocumented (unclear if it means clinical diagnosis or self-report) - the model is, and must be presented as, a statistical association, not a diagnosis. See `ml/dataset/README.md`.
- Dataset license (CC0) is taken on corroborating evidence, not a direct read of the original Kaggle listing (kaggle.com is outside this environment's network access) - see `ml/dataset/README.md`.
- Model-family screening and tuning used subsamples of the training data for compute reasons (this environment has a single CPU core); only the winning model's final fit and evaluation used the complete dataset. See `docs/ml-methodology.md`.
- ML prediction is unavailable for users with `gender = OTHER` (the dataset has only two gender classes) and for any assessment before every required profile field is filled in - the rule-based Health Score (Phase 3) remains available regardless.
- Predictions are a point-in-time snapshot, by design - there's no "regenerate with current profile" action, and the UI doesn't yet show how stale a stored prediction's underlying data might be.
- `health_predictions.feature_importance` stores the model's *global* importances (same for every prediction); the *per-prediction* SHAP breakdown is in `prediction_factors` / `shap_values` - these are deliberately different things stored side by side, documented in the model code, but easy to confuse when reading the table directly.
- **Notification scope:** mobile Phase D has opt-in local medicine reminders generated from real schedule rows. The `notifications` table still has no inbox API/write workflow; wellness reminders, web notifications, remote push, and email delivery are not implemented.
- **WEEKLY/MONTHLY medicine schedules only support one dose on a fixed cadence** (every 7 or 30 days from the start date) - there's no way to express "Monday/Wednesday/Friday" or a true calendar-month cadence. DAILY (the common case) is fully featured.
- **Schedule generation auto-extension**: Resolved via `ensure_schedule_ahead(db, medicine, days_ahead=90)`. Long-running active medicines dynamically auto-extend their schedule rows forward whenever `/today` or `/schedule` endpoints are queried, ensuring future doses continue rolling forward without a fixed cutoff.
- Editing a medicine's dosage, instructions, or notes does not regenerate schedule entries (correct - these don't affect *when* doses occur) but there is also no way to retroactively annotate already-generated entries with the new dosage if it changes mid-course; the schedule only tracks timing and taken/skipped state, not a dosage-at-the-time-it-was-taken snapshot.
- No frontend tests exercise the Medicines pages' React components directly (same limitation noted in earlier phases) - only the extracted validation logic is unit-tested, plus the live HTTP walkthrough above.
- **Goal progress is computed live, not stored as history** (deliberate scope decision - see `docs/api.md`'s Goals section and `goal_service.py`'s docstring). There is no "goal progress over time" trend chart; the schema's `goal_progress` table exists but is unused.
- **WEIGHT goal progress is a closeness-to-target measure, not progress from a starting point** - no baseline weight is captured when the goal is created, so two people starting at very different weights with the same target get the same treatment. Always disclosed via `progress_note` when shown.
- **EXERCISE/SLEEP goal windows are fixed at 7 days** and **MEDICINE_ADHERENCE at 30 days**, regardless of what the user types as the goal's `unit` label (e.g. a `unit` of "minutes/day" would still be evaluated as "minutes in the last 7 days" - the label is display-only, not parsed).
- **`OTHER`-type goals have no progress tracking at all** - no automatic source exists, and there's no manual progress-logging endpoint either.
- The **web** tracking tabs (`Track.jsx`) and Goals page still have no component-level UI tests; prior verification was via build and backend live HTTP walkthrough. Mobile Phase E now has router-flow tests in source, but those tests could not be run in the current environment.
- **Reports week selection & inline viewing**: Resolved in `web/src/pages/reports/Reports.jsx`. Users can now select and view any historical week's summary inline on the page using the week-picker dropdown or history list "View Report" actions, as well as download PDFs directly from the main card.
- **Insights only compare this week to the immediately preceding week** - no monthly/longer-term trend analysis, and if a user skips a week entirely, the "previous period" for the next report is simply whatever that skipped week's (empty) data was.
- **Report history has no pagination** - `GET /reports/weekly/history` is hardcoded to the most recent 20 reports with no `page`/`cursor` parameter.
- Recommendations are deliberately simple presence/absence nudges ("log your sleep"), not personalized advice - this is intentional (staying inside the project's no-medical-advice rule), not a gap to close later, but worth stating plainly so it isn't mistaken for an oversight.

### Explicit Scope & Known Limitations
- **Mobile Client Scope**: The React Native mobile app covers core daily tracking, medicine logging, adherence, notifications, and quick health entry. Web-first screens not yet ported to mobile include: Emergency Card, Doctor Appointments, Family Profiles, Goals Builder, and Timeline.
- **Machine Learning Scope**: Only the cardiovascular heart assessment uses trained machine learning (`ml/models/best_model.joblib`). Diabetes (ADA questionnaire), PCOS (Rotterdam criteria), and Fatty Liver (FIB-4) are rule-based clinical scoring algorithms.
- **External Dependencies**: Medicine OCR requires Google Cloud Vision credentials; Web push requires VAPID configuration; Transactional email requires SMTP/Resend configuration (memory stub used in tests); Remote mobile push in Expo Go requires standalone build / EAS project configuration.
