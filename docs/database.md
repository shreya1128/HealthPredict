# HealthPredict Database Architecture & Schema Specification

This document provides complete documentation of the relational MySQL database schema for the HealthPredict platform.

---

## 1. Schema Overview

The database is built on **MySQL 8.0+** (with full MariaDB 10.11+ compatibility) using `InnoDB` and `utf8mb4_unicode_ci`.
- **28 Normalized Tables**
- **1 Consolidated View (`user_health_summary`)**
- **Relational Integrity**: Foreign keys with `ON DELETE CASCADE` ensure child records (profiles, schedules, logs, assessments, doctor shares, caregiver invites) cleanly tear down when a user or parent entity is deleted.
- **Computed Fields**: Physical BMI calculation is implemented as a stored generated column to guarantee zero calculation drift between application and database.
- **Strict SQL Mode**: `STRICT_TRANS_TABLES,NO_ENGINE_SUBSTITUTION` is enforced on every session to prevent silent truncation.

---

## 2. Complete Table Catalog (33 Tables + 1 View)

### 2.1 Identity, Authentication & Profile Subsystem
1. **`users`**: Core identity table storing user credentials, role (`USER`, `ADMIN`), active status flag, and timestamps.
2. **`user_profiles`**: Clinical and physical baseline metadata: height, weight, waist circumference, blood type, allergy/condition JSON arrays.
3. **`user_tokens`**: Ephemeral authentication tokens: refresh tokens, password reset tokens, email verification tokens (persists SHA-256 digests).
4. **`token_blocklist`**: Revoked JWT access tokens identified by `jti` and expiry.
5. **`user_device_tokens`**: Native device push notification tokens (Expo Push tokens) with active flags and device platform.

### 2.2 Health Assessment & ML Prediction Subsystem
6. **`health_assessments`**: Primary health screening logs containing vital signs: systolic/diastolic BP, heart rate, blood glucose, SpO2, body temperature, rule-based 0-100 score, and JSON breakdown.
7. **`health_predictions`**: Point-in-time snapshot of the Gradient Boosting prediction linked 1:1 with `health_assessments` (score, risk_level, confidence, SHAP values).
8. **`health_history`**: Consolidated daily health metrics enabling rapid time-series queries for trend lines and graphs.
9. **`ml_model_info`**: Metadata record of trained ML models, active version, cross-validation metrics, and feature names.

### 2.3 Medication & Adherence Subsystem
10. **`medicines`**: Prescriptions managed by user: medication name, dosage, units, form (`TABLET`, `CAPSULE`, etc.), frequency, schedule timing JSON, instructions, `rxcui`, `quantity_on_hand`, `pills_per_dose`, `refill_threshold_days`, `pharmacy_note`, and active flag.
11. **`medicine_schedules`**: Granular dose instances generated by the schedule generator (`scheduled_date`, `scheduled_time`, `is_taken`, `is_skipped`, `taken_at`, `skipped_reason`, `dosage_at_intake`).
12. **`medicine_intake_logs`**: Daily aggregated adherence rollups per medicine (`taken_count`, `skipped_count`, `missed_count`, `adherence_percent`).
13. **`drug_interaction_cache`**: Persistent cache of drug-drug interactions verified via openFDA and RxNav APIs (`drug_a_name`, `drug_b_name`, `severity`, `description`, `source`).

### 2.4 Wellness Tracking & Goals Subsystem
14. **`exercise_logs`**: Daily workout records: exercise type, duration minutes, intensity, calories burned, distance km.
15. **`sleep_logs`**: Sleep journals: bedtime, wake time, computed sleep duration hours, and subjective 1–5 quality rating.
16. **`hydration_logs`**: Water consumption entries: volume in milliliters (`amount_ml`), entry timestamp, and optional notes.
17. **`nutrition_logs`**: Meal logs: meal type (`BREAKFAST`, `LUNCH`, `DINNER`, `SNACK`), food description, calories, portion size, and macronutrient JSON.
18. **`wellness_goals`**: Active and past health targets across 6 goal types: `EXERCISE`, `SLEEP`, `HYDRATION`, `WEIGHT`, `MEDICINE_ADHERENCE`, `OTHER`.
19. **`goal_progress`**: Time-stamped progress entries toward specific wellness goals.

### 2.5 Clinical Collaboration & Emergency Subsystem
20. **`care_profiles`**: Profiles for dependents and family members managed under a single account (`full_name`, `relationship`, `date_of_birth`, `gender`).
21. **`caregiver_access`**: Secure caregiver invitations with configurable permissions (`access_level`: `VIEW_ONLY` / `EDIT`, `notify_missed_dose`).
22. **`doctor_shares`**: Cryptographically secure, expiring read links for physician consultations with doctor writeback notes.
23. **`doctor_appointments`**: Calendar of upcoming and past medical consultations (`doctor_name`, `specialty`, `location`, `appointment_date`, `status`).
24. **`emergency_cards`**: Fast-access emergency profile (`public_token`, `blood_type`, `allergies`, `emergency_contact_phone`, `organ_donor`, `is_public`).
25. **`symptom_logs`**: Patient symptom tracking (`symptom_name`, `severity` 1-5, `logged_at`, `notes`).

### 2.6 Reporting, Notifications & Governance Subsystem
26. **`weekly_reports`**: Pre-computed weekly wellness rollups (Monday-to-Sunday): average health score, weight delta, total workout minutes, average sleep, hydration, and medication adherence percentage.
27. **`notifications`**: In-app notification inbox records for web and mobile clients: type, title, message, read flag, and deep-link action URL.
28. **`admin_audit_logs`**: Administrative compliance log recording user activation/deactivation, admin identity, target entity, old/new states, IP address, and status.

### 2.7 Views
- **`user_health_summary`**: Consolidated user health view combining active medicines, current day vitals, and total assessments.

---

### 2.8 Screenings & Cycle Tracking Subsystem (added in migrations 012–014)
- **`diabetes_screenings`**: FINDRISC / ADA non-invasive diabetes risk screening records, scoped per care profile.
- **`menstrual_logs`**: User-controlled cycle tracking (period dates and duration, flow, symptoms), scoped per care profile.
- **`pcos_screenings`**: Educational PCOS symptom screenings aligned with the Rotterdam consensus criteria. Informational only, not a diagnosis.
- **`fatty_liver_screenings`**: Cardiometabolic risk-factor awareness screenings based on MASLD consensus. Informational only, not a diagnosis.

### 2.9 Doctor-share notes (added in migration 009)
- **`doctor_share_notes`**: Physician notes and recommendations left on a shared record via a doctor-share link.

## 3. Database Migration & Initialization

The schema is defined declaratively in `database/schema.sql`. All migrations are sequentially numbered in `database/migrations/`:
- `001_care_profiles.sql`
- `002_doctor_shares.sql`
- `003_emergency_symptoms_appointments.sql`
- `004_device_tokens_and_notifications.sql`
- `005_scheduling_and_goals_enhancement.sql`
- `006_security_and_interoperability.sql`
- `007_medicine_intelligence.sql`

To apply schema to a clean database:
```bash
mysql -u hp_user -p healthpredict < database/schema.sql
```
