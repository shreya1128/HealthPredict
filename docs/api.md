# API Reference (implemented endpoints)

Base URL `http://localhost:8000/api`. Live, interactive docs: `/api/docs`.
Protected routes need `Authorization: Bearer <access_token>`. Errors are `{"detail": "..."}`;
validation errors (422) also include `errors: [{field, message}]`. Server errors never include stack traces.

Endpoints for later phases (prediction, medicines, tracking, goals, reports, notifications,
most admin routes) were described in `architecture.md`; the admin routes below were implemented in Phase F.

## Authentication - `/auth`
| Method | Path | Auth | Notes |
|---|---|---|---|
| POST | `/auth/register` | - | 201 -> user. 409 if email exists (case-insensitive). 422 on weak password / mismatch. |
| POST | `/auth/login` | - | 200 -> `{access_token, refresh_token, token_type, expires_in, user}`. 401 same message for unknown email or wrong password. 403 if deactivated. |
| POST | `/auth/refresh` | - | Body `{refresh_token}`. Rotates: each refresh token works once. Reusing an old one revokes all of that user's sessions. |
| POST | `/auth/logout` | - | Body `{refresh_token}`. Idempotent. |
| POST | `/auth/forgot-password` | - | Always the same 200 message (no account enumeration). |
| POST | `/auth/reset-password` | - | Body `{token, password, confirm_password}`. Single use; signs the user out everywhere. |
| POST | `/auth/verify-email` | - | Body `{token}`. |
| GET | `/auth/me` | user | Current user. |

`register`, `login`, `refresh`, `forgot-password`, `reset-password` are rate limited per IP (429).

Password rules: 8+ chars, upper, lower, digit, special, at most 72 bytes (bcrypt limit).

## Profile - `/profile` (user)
| Method | Path | Notes |
|---|---|---|
| GET | `/profile` | `{user, height_cm, weight_kg, bmi, ...}`. `bmi` is generated by the database. |
| PUT | `/profile` | Partial update: only fields you send change. Unknown fields (e.g. `role`) are rejected with 422. |

Ranges: height 50-250 cm, weight 20-400 kg, waist 30-250 cm, sleep 0-24 h, water goal 500-10000 ml.
`exercise_frequency`, `smoking_status`, `alcohol_consumption`, `cholesterol_level` are `null` until
the user sets them - there is no default. A health-assessment score computed before they're set
will report those components as skipped rather than assuming a value (see
`docs/health-scoring.md`); an ML prediction (below) requires them to be set at all.

## Health assessment - `/health` (user)
Scoring methodology: `docs/health-scoring.md` (rule-based score) and `docs/ml-methodology.md`
(ML prediction) - two separate, independently-computed numbers on the same response. Every
response includes `disclaimer` (the rule-based score's, always shown) and, when relevant,
`glucose_caveat` and `profile_hints` (nudges toward completing the profile - never blocking).

| Method | Path | Notes |
|---|---|---|
| POST | `/health/assessment` | Body: any subset of `systolic_bp`+`diastolic_bp` (must be a pair), `heart_rate_bpm`, `blood_glucose_mg_dl`, `spo2_percent`, `temperature_celsius`, `assessment_notes`. At least one vital required (422 otherwise). Combines with the caller's profile; missing data is excluded and remaining weights rescale (see `data_completeness_percent`, `score_breakdown.skipped`). Also upserts today's row in the trend history, and - if every required field is available (see below) - computes and stores an ML prediction. |

**ML prediction fields** (also on the response): `ml_prediction` is `null` unless every one of the
model's required inputs (date of birth, gender as Male/Female, height+weight, cholesterol level,
smoking/alcohol/exercise, and this assessment's blood pressure + glucose) came from real,
user-provided data - never imputed. When `null` for that reason, `ml_prediction_missing_fields`
lists what to add. When present, `ml_prediction` has `probability`, `risk_level`,
`confidence_percent`, `model_version`, `top_factors` (SHAP-ranked, each with `direction` and
`relative_strength` - a relative influence rank, not a probability-point breakdown; see
`docs/ml-methodology.md`), `explanation_text`, and its own `disclaimer`. Predictions are computed
once at assessment creation and are not recomputed if the profile changes afterward.
| GET | `/health/assessment/{id}` | Full detail incl. `score_breakdown`. 404 (not 403) if it belongs to someone else. |
| GET | `/health/assessment/latest` | Most recent assessment. 404 if none exist yet. |
| GET | `/health/assessment/history?page&page_size` | Paginated summaries, newest first. |
| GET | `/health/history?days=30` | One point per day (1-365) from the trend table, for charting. |

## Medicines - `/medicines` (user)
Schedule generation methodology: `backend/app/utils/schedule_generator.py` (pure function, 13
unit tests). `DAILY` generates one dose per entry in `time_of_day` every day; `WEEKLY`/`MONTHLY`
generate one dose per period (every 7 / 30 days) at `time_of_day[0]` - documented limitation: no
specific-weekday scheduling (e.g. "Mon/Wed/Fri") yet. `AS_NEEDED` generates no schedule rows.
Generation produces an initial 90-day horizon from `max(today, start_date)` and is dynamically
extended forward as time progresses via `ensure_schedule_ahead(db, medicine)` on queries to
`/today` and `/schedule`.

| Method | Path | Notes |
|---|---|---|
| POST | `/medicines` | `time_of_day` required (list of `"HH:MM"`) unless `frequency_unit` is `AS_NEEDED`, in which case it must be empty. Generates the schedule immediately. |
| GET | `/medicines?active_only=` | List the caller's medicines, active first. |
| GET | `/medicines/today` | Today's schedule entries across all *active* medicines, with `medicine_name` attached, ordered by time. |
| GET | `/medicines/{id}` | 404 if not owned. |
| PUT | `/medicines/{id}` | Partial update. Changing `frequency_unit`, `time_of_day`, or `end_date` regenerates *future, not-yet-acted-on* schedule entries only - anything already marked taken or skipped is never touched or deleted, verified directly (see `STATUS.md`). `is_active: false` pauses (excluded from `/today` and future generation, but history is kept); `true` resumes. |
| DELETE | `/medicines/{id}` | Cascades to its schedule and intake logs. |
| GET | `/medicines/{id}/schedule?past_days=7&upcoming_days=14` | Schedule entries in that window (each 0-90). |
| POST | `/medicines/{id}/schedule/{schedule_id}/taken` | Marks taken, clears any skip. |
| POST | `/medicines/{id}/schedule/{schedule_id}/skipped` | Body `{reason?}`. Marks skipped, clears any taken state. |
| GET | `/medicines/{id}/adherence?days=30` | `{scheduled_count, taken_count, skipped_count, missed_count, adherence_percent}` over the window (1-365 days). `missed` = past, unacted-on entries; today's pending entries are never counted as missed. |
| GET | `/medicines/adherence/overall?days=30` | Same fields plus `days`, across all **active** medicines combined (paused ones excluded). `adherence_percent` is `null` (not 0) when nothing has been scheduled yet. Added in the mobile Phase D. |

**Not included:** server-side reminders and push delivery. The mobile app schedules *local* on-device dose reminders from `/medicines/{id}/schedule` (the server sends nothing). The in-app inbox is described under Notifications below.
(Phase 1 schema) but nothing in this phase writes to it or schedules anything - "today's
medicines" must be checked by visiting the dashboard. Push/in-app reminder delivery is deferred
to a later phase; see `STATUS.md`.

## Goals - `/goals` (user)
Progress is computed **live** on every read from the actual tracking data - never a stored,
potentially-stale snapshot (verified directly: deleting all underlying logs immediately reverts a
goal to its no-data state on the next GET). `database/schema.sql`'s `goal_progress` table (a
historical snapshot log) is intentionally unused - see `app/services/goal_service.py`'s
module docstring.

| Method | Path | Notes |
|---|---|---|
| POST | `/goals` | `goal_type` one of `EXERCISE`/`SLEEP`/`HYDRATION`/`WEIGHT`/`MEDICINE_ADHERENCE`/`OTHER`. `target_value` must be positive. |
| GET | `/goals?status=` | Each item includes `current_value`, `percentage_complete` (capped at 100), and `progress_note` (set only when percentage can't be computed - e.g. no data yet, or `OTHER` which has no auto-source). |
| GET | `/goals/{id}` | |
| PUT | `/goals/{id}` | Setting `status: "COMPLETED"` also sets `is_achieved: true`. Goals are **not** auto-completed at 100% - the user marks completion themselves (keeps GET side-effect-free). |
| DELETE | `/goals/{id}` | |

What each `goal_type` measures (fixed windows - a goal's `unit` is a free-text display label, not
parsed to change the window):
- `EXERCISE` - total `duration_minutes` logged in the last 7 days.
- `SLEEP` - average `sleep_duration_hours` over the last 7 days.
- `HYDRATION` - today's total `water_intake_ml` (0 is a valid value, not "no data").
- `WEIGHT` - current `user_profiles.weight_kg`, compared to the target as **closeness**, not
  progress-from-a-starting-point (no baseline weight is captured at goal creation) - `progress_note`
  always explains this when a percentage is shown.
- `MEDICINE_ADHERENCE` - taken/scheduled across all active medicines, last 30 days.
- `OTHER` - no automatic source; `current_value`/`percentage_complete` are always `null`.

## Dashboard - `/dashboard` (user)

| Method | Path | Notes |
|---|---|---|
| GET | `/dashboard` | One aggregated payload: `latest_assessment`, `today_medicines`, `hydration_today`, `exercise_this_week`, `sleep_this_week`, `active_goals`, `insights`. Pure composition of other services' already-tested logic - no new business logic lives here. Degrades gracefully for a brand-new user with no data (every field is an empty list/zero/null, never a 500). |

## Reports - `/reports/weekly` (user)
Weeks run Monday-Sunday; `week_start` is normalized to that week's Monday regardless of which
day within the week is passed. Insights reuse `app/utils/wellness_insights.py` (17 unit tests),
comparing this week's aggregates to the immediately preceding week - a metric is only mentioned
if it changed by more than 10%, to avoid noisy claims from small fluctuations. Never implies
causation (same rule as the Phase 5 SHAP explanations).

| Method | Path | Notes |
|---|---|---|
| GET | `/reports/weekly?week_start=` | Computes the report and **upserts it into history** (viewing a week is what makes it exist as history - idempotent per user+week, safe to call repeatedly e.g. on every dashboard visit). Defaults to the current week. |
| GET | `/reports/weekly/history` | Past reports, newest first. |
| GET | `/reports/weekly/{id}/pdf` | Downloads a PDF (ReportLab) built from that **stored** report row - a historical PDF reflects the data as it was captured, not recomputed against today's live data. `recommendations` are app-navigation nudges for missing data (e.g. "log your sleep"), never medical advice. |

PDFs are rendered on demand, not cached to disk (`weekly_reports.pdf_file_path` is unused) - fast
enough to regenerate each time from the stored metrics.

## Admin - `/admin` (role ADMIN, else 403)
The role is re-checked against the database on every request. **Every statistic is an aggregate; no endpoint returns an individual's
health measurements.** Every state-changing action is written to the audit log.

| Method | Path | Notes |
|---|---|---|
| GET | `/admin/users?page&page_size&search&status=active\|inactive&role=USER\|ADMIN` | Account data only (adds `last_login`) - no health data, no password hashes. `page_size` max 100. |
| PATCH | `/admin/users/{id}/status` | Body `{is_active, reason?}` (`reason` max 500). Deactivated accounts are rejected on their next request, at login and at token refresh. **An admin cannot change their own status** (400, recorded as a FAILED audit entry), which also guarantees at least one active admin always remains. Asking for the state the account is already in is a no-op (no audit entry). Unknown id: 404. |
| GET | `/admin/stats/overview` | Account counts (total, active, inactive, admins, new in 7/30 days, signed in 7/30 days, never signed in) and assessment counts (total, 7/30 days, stored AI predictions). |
| GET | `/admin/stats/risk` | Each **member's latest assessment**, counted once (admins excluded): rule-based LOW/MODERATE/HIGH counts, AI-estimate counts, members with/without an assessment, average health score, average AI probability. Averages are `null` when there is no data. |
| GET | `/admin/stats/trends?days=30` | `days` 7-365. One point per UTC day (zero-filled): new users, assessments, predictions. |
| GET | `/admin/stats/usage?days=30` | Per feature (assessments, exercise, sleep, hydration, nutrition, medicines, goals, reports): records created and distinct users in the window; platform medication adherence (taken / scheduled for active medicines of active users; `null` if none scheduled). |
| GET | `/admin/ml/model` | Model details read from the training artifacts (`ml/saved_models/model_info.json` and `model_comparison.json`): selected model, hyperparameters, train/test sizes, **held-out test metrics + confusion matrix**, the 4-model **cross-validated** comparison, whether the serving model is loaded, and real usage counts from stored predictions. If artifacts are missing or unreadable it returns `available: false` with a note, never invented numbers. |
| GET | `/admin/audit-logs?page&page_size&action_type&admin_id&status=SUCCESS\|FAILED` | Newest first, with the acting admin's name/email. Actions: `USER_DEACTIVATED`, `USER_REACTIVATED`. |

Definitions: *signed in* uses `users.last_login`, which is set at login only, so sessions kept alive by token refresh are not counted.
Windows are UTC. The `ml_model_info` table is not used (the artifacts are the source of truth).

| Method | Path | Notes |
|---|---|---|

| GET | `/notifications/unread-count` | `{unread}` |

| POST | `/notifications/read-all` | `{updated}` |
| POST | `/notifications/{id}/read` | Idempotent. Someone else's id is **404**, not 403. |
